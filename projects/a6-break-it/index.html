Break It Yourself

Five ways to use good cryptographic primitives badly, each with the attack that follows. Nothing here is staged: every result on this page is computed in your browser by the same code the tests run against, including the AES and SHA-256 implementations. Press a button and watch something break.

1 · ECB penguin 2 · Nonce reuse 3 · Padding oracle 4 · Length extension 5 · Timing leak

1 · The picture that survives encryption

The mistake: encrypting with a block cipher directly, one block at a time. AES-128 in ECB mode

total break difficulty: none

A block cipher maps each 16-byte block to a ciphertext block, and does it the same way every time. Identical input blocks therefore produce identical output blocks, so anything repetitive in the plaintext, like the flat background of an image, stays visibly repetitive after encryption.

The fix: never use a bare block cipher. Use an AEAD mode such as AES-GCM, which chains blocks and authenticates the result.

2 · One keystream, many messages

The mistake: reusing a nonce, so two messages are XORed with the same keystream. AES-CTR with a repeated nonce

plaintext recovery difficulty: statistics

A stream cipher turns the key and nonce into a keystream and XORs it with the message. Use the same nonce twice and the keystream cancels: c1 XOR c2 = m1 XOR m2. The key never enters the attack at all.

3 · A server that only says "bad padding"

        failed. CBC without a MAC

4 · Appending to a message you cannot read

      

        The mistake: building a MAC as H(secret || message).
        SHA-256, a Merkle-Damgard hash
      

    

    

      forgery
      difficulty: arithmetic
    

  


  

    SHA-256 processes a message block by block, and its output is its
    internal state. Anyone holding a digest can therefore carry on hashing from
    where it stopped, without knowing what came before. Prefixing a secret
    protects nothing against appending.
  


  

    

      
      
      
      
      
      
      

        
        
      

      

        The secret itself is random and never shown to the attack. Only its
        length is guessed, and a wrong guess is rejected, so an attacker simply
        tries every plausible length.
      

    


    

      
What the server receives

      

      

        The middle section is the glue padding: the bytes
        SHA-256 would have appended to the original message. The attacker
        cannot avoid sending them, and a server that parses loosely does not
        care.
      

      

    

  


  

    The fix: use HMAC, which hashes the key on both sides of
    the message so a digest cannot be resumed. The page verifies its HMAC
    against WebCrypto in the tests.
  







  

    

      
5 · Guessing a token by watching the clock

      

        The mistake: comparing secrets with a loop that stops at the first
        wrong byte. non-constant-time comparison
      

    

    

      key recovery
      difficulty: measurement
    

  


  

    A comparison that returns as soon as it finds a mismatch takes slightly
    longer when more of the guess is right. Guess one character at a time,
    keep the slowest, and the token falls out in a linear number of tries
    instead of an exponential one.
  


  

    

      

        
      

      

        
        
      

      

      

        Each candidate is timed over many repetitions with
        performance.now(), and the comparison itself
        does inflated per-byte work. Browser clocks are deliberately coarse, so
        this amplifies a real effect rather than inventing one:
        the same signal exists in a normal comparison, just below the timer's
        resolution.
      

      

        The last character is the exception, and the demo does not pretend
        otherwise. Each byte's work happens before its comparison, so at the
        final position a right and a wrong guess cost exactly the same and the
        timing difference is zero. With the other seven known there are only
        sixteen candidates left, so that one is settled by simply asking the
        server which token it accepts.
      

    


    

      
Time per candidate character

      

        The tallest bar is the correct next character. With the constant-time
        comparison switched on, the bars flatten out and the attack fails.
      

      
      

        token
        

      

      

    

  


  

    The fix: compare secrets in constant time, touching every
    byte regardless of where they differ. Most languages ship one, and it costs
    nothing.
