Taint Analyzer

Paste code in, and this proves whether untrusted input can reach a dangerous sink — a database query, eval, innerHTML — without being sanitized first, and shows the exact path the data took. Underneath: a real control-flow graph and a worklist dataflow analysis, both drawn on screen instead of hidden in a report.

Most break-ins start the same way: something a stranger typed into a web form travels through a program and ends up somewhere it is treated as an instruction rather than as text, such as a database query. A security scanner is meant to find those routes before an attacker does, and normally it prints a verdict and keeps its reasoning to itself. This page runs that reasoning in front of you and shows the exact route it found.

Control-flow graph

blocks coloured by lattice state · click a finding to animate its witness path

Every route the program can take, drawn as a map (a control-flow graph). Each box is a run of statements with no branching in it; the arrows are the jumps a branch or a loop can make. The analysis has to consider every route, because an attacker gets to pick which one runs.

A red box is a point in the program where tainted data is live. Click a finding above and the map shows the specific route the data took to get to the dangerous call.

Fixed-point stepper

watch the worklist algorithm converge, one block visit at a time

The tool cannot simply read the program top to bottom, because a loop can send data backwards, and a checker that naively followed the loop round would never finish. This one is guaranteed to finish: what it knows about a box only ever grows, there are finitely many variables to learn about, so re-examining boxes until one full pass changes nothing anywhere has to run out of changes. Each click below is one of those re-examinations (the worklist algorithm reaching its fixed point).

Each step below is one block being pulled off the worklist and re-processed. Its IN set is the union (join) of its predecessors' OUT sets; its OUT set is what falls out after running every statement in the block. When a block's OUT set stops changing, it stops re-queueing its successors — that is the fixed point.

That guarantee is the reason a scanner can promise an answer on a program with loops at all, rather than a timeout.

What "sound" means here

An analysis like this can be sound (never miss a real bug) or precise (never raise a false alarm) but rarely both. This one is built sound-leaning: see the README for exactly where it over-approximates, and what it flat out cannot see.

In plain terms: this tool would rather warn you about something harmless than stay quiet about something real. That is a deliberate choice, and it is the choice every scanner has to make one way or the other.
