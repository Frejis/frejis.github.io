Writeup · A4

The part of a fuzzer nobody shows you

7 minute read property testing · shrinking · delta debugging

Random testing is easy to explain and easy to dismiss. The part that makes it usable in practice is the part that never gets demonstrated.

Open the demo

1The problem

Property-based testing sounds like a gimmick when described: throw random inputs at a function and check a rule instead of writing examples. The obvious objection is that random failures are useless. A test that reports "this failed on [7,3,19,0,4,11,...] with 34 more elements" has told you a bug exists and given you nothing to work with.

The answer is shrinking, and shrinking is the piece that never appears in a conference slide. Tools like QuickCheck, Hypothesis and fast-check do it silently and print only the final, tidy counterexample, so the reader concludes the tool got lucky. The work is in between, and it is invisible.

2What I built

A miniature property-based testing engine written from scratch, with the shrinking step drawn on screen. Pick one of the functions under test, press Run, and the page fires hundreds of seeded random inputs at it, checking a property: sorting twice is the same as sorting once, reversing twice is the identity, decode(encode(s)) equals s, binary search finds every element that is present, concatenation preserves total length.

Some of the subjects are genuinely buggy. When one fails, the engine starts simplifying the counterexample, and every candidate it tries becomes a row in a table and a point on a descending chart. You watch a large array collapse into the two elements that actually matter. Because the generator is seeded, the whole run is reproducible.

3How it works

Randomness comes from a SplitMix32 PRNG, chosen for being tiny and reproducible from a seed. The interesting design decision is in the generators. Each one does not produce a value; it produces a Shrinkable, which is a value plus a lazily computed list of simpler Shrinkables. That is what makes the whole thing compose: map, filter, tuple and array can shrink their children without knowing anything about what those children are. You cannot shrink 23 toward 0 without knowing it came from int(0, 100), and you cannot shrink an array of them without each element carrying its own shrinker. Strings get it for free by being generated as arrays of character codes and mapped to text.

Array shrinking is delta debugging in miniature. Removing one element at a time is far too slow to get from forty elements to two, so the shrinker first proposes the empty array, then removes contiguous chunks of size n/2, halving the chunk size on each pass in the manner of ddmin, and only once the length has stopped falling does it shrink individual surviving elements. The search itself is greedy: it takes the first simpler candidate that still fails, in generator order, and continues from there.

The bugs are real bugs rather than straw men. sort() with no comparator, which sorts lexicographically and so puts 10 before 9. An off-by-one on a binary search loop bound, which misses elements only at particular positions. A run-length encoder that silently corrupts on runs of ten or more identical characters. A calendar function that treats every month except February as thirty days. Each is the sort of defect that survives a handful of hand-written examples and only shows up under random pressure.

4What was hard

Getting the shrink path to be trustworthy. It is easy to write a shrinker that produces a smaller value which no longer triggers the bug, and it looks fine on screen because the numbers went down. The property the code must maintain is that every accepted step on the path is itself a genuine failure, and that the final counterexample still fails the property. Both are asserted in the tests, over the whole path, not just at the ends.

The chunk-removal strategy also has to be ordered carefully. If element shrinking runs before length reduction, the search spends its budget minimising numbers inside an array that is about to be thrown away. Length first, contents second, is what turns an impractical number of candidates into a handful.

5What it is not

  • Not a replacement for fast-check or Hypothesis. No integrated shrinking of recursive or mutually defined generators beyond arrays, tuples and mapped values, no generation from types, no coverage guidance.
  • No stateful or model-based testing. Every property is a pure function of freshly generated arguments, which leaves out where tools like Hypothesis earn most of their keep.
  • Shrinking is greedy, not minimal. It accepts the first simpler failing candidate and moves on; a different generator order can produce a different, still valid, result.
  • The PRNG is a plain SplitMix32, chosen for speed and reproducibility, not for distribution quality or cryptographic strength.
  • The size metric is a rough proxy — array or string length, or a number's magnitude — used for the chart and the reduction statistic, not a formal notion of counterexample complexity.
