Telling a lead apart from a coincidence

8 minute read pivoting · selectivity · force-directed layout

Two servers sharing a fingerprint might be the same operator, or might be two of the forty thousand machines running the same default install. The difference is arithmetic, not intuition.

Open the demo

1The problem

Infrastructure attribution works by pivoting. You start from one host, notice something it exposes — a TLS certificate, an SSH host key, the hash of its favicon — and ask which other hosts expose the same thing. Repeat, and a set of apparently unrelated servers turns into a cluster with a shape to it.

The failure mode is obvious once stated and easy to walk into anyway. Not every shared trait means anything. Two hosts sharing a self-signed certificate almost certainly share an operator. Two sharing a TLS client fingerprint may share nothing but a version of OpenSSL, and two behind the same large cloud provider share a landlord. A pivot tool that treats those three the same will grow a "cluster" out of background noise, and the graph it draws will look every bit as convincing as a real one.

2What I built

Ninety synthetic hosts, each carrying a certificate fingerprint and issuer, an SSH host key fingerprint, a JA3 TLS client fingerprint, a favicon hash, a server header and a hosting provider. Start from one host and every artifact it has is offered as a pivot, labelled with how many hosts carry that same value and colour-coded by what that count is worth. Take a pivot and the selection grows to every matching host while a force-directed graph redraws around the new cluster. A trail on the right records each step, so you can walk back.

There is also a button labelled "pivot on a common trait", which does exactly that and floods the selection with unrelated hosts. It makes the point physically rather than in a caption: this is what following a worthless trait feels like.

3How it works

The core idea is selectivity. For an artifact value, computeSelectivity in selectivity.js counts how many of the ninety hosts carry it and turns that count into a score of 1 − (count − 1)/total, so a value unique to one host scores 1 and a near-universal one scores near 0. On top sit two absolute thresholds: at most five hosts is strong evidence, at most fifteen is worth noting, above that is background. Host counts rather than ratios read sensibly at this dataset's size, and they live in one place. That score drives the tag colour on every pivot option and the ranking of candidates.

Pivoting itself is deliberately plain. applyPivot takes a session and returns a new one, never mutating the input, with the matching host IDs unioned into the selection and the step appended to a history recording the field, the value, which hosts were newly added and the selectivity that added them. Undo recomputes from the start host by replaying the remaining steps rather than subtracting the last one, because a later pivot may have re-added a host an earlier one also brought in, and subtraction would quietly remove it.

The dataset comes from a fixed seed, but its structure is code rather than chance: which host indices belong to which cluster and which artifacts they share is written out explicitly, while only the artifact values and the noise hosts' fields come from the generator. That makes "does pivoting actually reach cluster C" a testable claim instead of a hope about a random layout.

Each of the four planted clusters has the same deliberate shape. A core of three or four hosts shares a strong artifact — a self-signed certificate and SSH key, a distinctive favicon, a private certificate authority — and one further host shares exactly one trait with exactly one member of that core. A single pivot finds the core and misses the bridge; you have to pivot again, from the right host, to reach it. That is the honest shape of the work: the first pivot is never the answer.

4What was hard

Making "this trait is worthless" something the user feels rather than reads. Any tool can print a confidence number next to a result. The version that teaches something has to let you take the bad pivot and watch a coherent handful of hosts dissolve into a crowd with nothing in common, which meant building realistic noise into the dataset: a JA3 hash on roughly sixty per cent of hosts because it is just what a common TLS library's handshake looks like, and a provider ASN behind a large slice of the rest.

Wiring the bridge hosts into a seeded generator was the fiddly part. Every artifact value comes out of the PRNG, but the relationships have to be exact — this host shares the SSH key and not the certificate, that one shares a rare JA3 with precisely one core member — and survive the noise overlays applied afterwards. That took more care than the force layout.

The last decision was about the subject matter. Scraping real data would have been simple and wrong for something published on a portfolio site, so everything is manufactured locally: IP addresses from the RFC 5737 documentation ranges, domains from the RFC 2606 reserved TLDs, organisation names invented. Nothing can collide with a real host.

5What it is not

  • Every row is synthetic. Hosts, IPs, certificates and organisation names come from a fixed seed. None of it was observed, scraped or looked up, and no real host, IP range or organisation appears anywhere in the dataset.
  • No network calls of any kind. Everything is computed in the browser from data built at load time. It does not talk to Shodan, Censys, VirusTotal or anything else.
  • Not a scanning or ingestion tool. Real attribution platforms index internet-wide scan data and certificate transparency logs continuously. This imitates none of that.
  • The selectivity thresholds are chosen, not derived. Five and fifteen hosts are sensible cutoffs for a dataset of ninety, not a model of how rare a fingerprint is on the real internet.
  • A model of the reasoning, not the work. The question it answers is which artifacts corroborate a link and which do not. Doing that against real infrastructure is a different job.
