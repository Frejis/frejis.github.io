A chain of trust, broken one link at a time

8 minute read ECDSA · WebCrypto · certificate chains

A signature that verifies tells you almost nothing on its own. What matters is which link in the chain behind it broke, and which ones did not.

Open the demo

1The problem

Digital signatures are usually taught as a single yes-or-no question: the signature is valid, or it is not. That framing is where most of the confusion about certificates comes from, because a browser padlock is not the answer to one question. It answers a sequence of them, asked of a chain of certificates, each vouching for the next.

The consequence is that "invalid certificate" is one of the least informative errors in computing. An expired intermediate, a signature that does not match, and a root nobody has agreed to trust are three different failures with three different fixes, and a verifier that stops at the first problem it meets cannot tell you which one you have. Worse, it encourages the belief that a broken link contaminates the rest of the chain, which is not how the mathematics works at all.

2What I built

Part 1 is the plain case. Type a message, press sign, and the page generates a real ECDSA key pair with the browser's own WebCrypto and signs the bytes of your text. The public key and the signature are shown in hex. Then there are three buttons that break it: alter the message, alter the signature, or verify against the wrong sender's key.

Part 2 is the part worth the visit. It builds a three-certificate chain — a root CA, an intermediate, an end certificate — and lets you attack any single link: corrupt the root CA's signature, expire the intermediate, or remove the root from the trusted set. Each attack lights up exactly one link with the reason it failed, and the other two keep reporting themselves as fine. Trust in a chain is not one verdict, it is a list of them.

3How it works

Signing is ECDSA over P-256, done by crypto.subtle rather than reimplemented. Curve arithmetic is not the interesting part here and a hand-rolled version would be a liability rather than a demonstration; the interesting part is what gets signed and what a verifier does with the result.

A certificate here is a plain JavaScript object with the five fields the trust story actually needs: subject, issuer, notBefore, notAfter, and the subject's public key. Issuing one serialises exactly those fields, in a fixed order defined by canonicalFields in trust-chain.js, and signs the resulting bytes with the issuer's private key. The fixed order is the whole reason it works: signer and verifier must produce byte-identical input or the check fails for a reason that has nothing to do with trust. This is deliberately not X.509 or DER, which sidesteps ASN.1 entirely and keeps the signed bytes readable straight out of the source.

validateChain walks the chain from root to leaf and, for each certificate, asks three independent questions: does its signature verify under its issuer's public key (for the root, its own), is it in date, and — for the root only — is its key in the trusted set. The first failing answer becomes that link's reason, drawn from a small enumeration: signature-invalid, expired, untrusted-root. Crucially the loop does not return early. Every link is evaluated whatever happened to the ones before it, and the result is a list of per-link verdicts alongside a single overall boolean.

That is what makes the demo honest rather than merely colourful. If you expire the intermediate, the leaf's own signature check still passes, and it should: the leaf's signature genuinely does not depend on whether its issuer's certificate is in date. The chain is invalid, the leaf link is not, and saying so precisely is more useful than a blanket red cross. The tests assert on which link fails and with which reason, not just that validation returned false.

4What was hard

Resisting the early return. The natural way to write a chain validator is to bail the moment something is wrong, and for a production verifier that is correct — there is no reason to keep computing once trust is gone. But it destroys the only thing this page exists to show. Getting it right meant separating the per-link verdict from the overall one, so the UI can display "this link broke, these did not" without the code pretending a broken chain is acceptable.

The second difficulty was canonicalisation, the classic place signature systems go wrong. Signing a serialised object means the exact bytes matter, and JavaScript object key order is close enough to predictable that a bug here hides for a long time before surfacing. Pinning the field set and order in one named function, used by both the issuing path and the verifying path, is the smallest structure that makes the mistake impossible rather than unlikely.

The attacks also had to be real. Faking a failure with a flag would have been easy; instead each one mutates the actual data — a byte of the signature, a date field, the trusted-root list — and the same validator that reports success reports the failure.

5What it is not

  • Not X.509. Certificates are plain JS objects signed over canonical JSON. There is no DER parsing, no ASN.1, and nothing here would read a certificate a real CA issued.
  • No extensions. No basic constraints, key usage, path-length limits or name constraints — the fields a real validator spends most of its code on.
  • No revocation. Neither CRL nor OCSP. A compromised certificate stays valid here until it expires.
  • No chaining rules beyond signature and dates. A real validator checks that the issuer name matches, that the issuer is permitted to be a CA at all, and much else.
  • Keys live for one page load. Key pairs are generated fresh in memory every time the page opens and never touch disk. No key management, no storage, no CA that outlives the tab.

It demonstrates the shape of the trust problem and the precision a verifier can offer when it is written to be informative. It is not a PKI implementation.
