Writeup · A14

A message either arrived or it died somewhere, and you should be able to point at where

8 minute read HL7 v2 · FHIR · idempotency · pipelines

Clinical integration work is mostly answering one question under time pressure: this lab result did not show up, why not. A pipeline that cannot answer it precisely is a pipeline you debug by reading logs sideways.

Open the demo

1The problem

Hospital systems talk to each other in formats older than most of the software around them, and they talk constantly. The team behind MidtEPJ in Region Midtjylland moves on the order of 80,000 messages a day between systems and reports around 150,000 registrations a day onward to national registries, for a record more than 30,000 staff use. At that volume the interesting question is never whether the happy path works, but what happens to the fraction that does not.

A message can die of many different things: text that is not a valid segment, a patient identifier of the wrong shape, a lab code nobody mapped, a value no human body could produce, the same message arriving twice, a receiving system that is down. A pipeline reporting all six as "error" has thrown away the only information that makes them actionable, and if the stages are sloppily assigned, two faults surface at the same place and the report lies about which one happened.

2What I built

A lab result moving through seven stages — receive, parse, validate, transform, enrich, route, deliver — with the trace drawn across the top of the page as seven boxes: green for a stage that passed, red for the one that rejected, grey for the stages that never ran. Click a box for what it checked and concluded.

Six fault buttons inject a specific, realistic problem into a valid message, each failing at a different stage, so the strip lights up somewhere new every time. Rejected messages land in a dead-letter panel where you can edit the text and replay it: fix the real problem and it clears, repeat the mistake and it stays queued. A throughput run pushes thousands of messages through with a configurable fault mix and accounts for every one — delivered, duplicate, or rejected at a named stage — with the counts summing exactly to the total.

3How it works

The wire format is a subset of HL7 v2: four pipe-delimited segment types, MSH, PID, OBR and OBX, enough to carry one lab result end to end. MSH has a well-known quirk the parser handles explicitly: the | immediately after MSH is field 1, the field separator declaring itself, so every subsequent field in that segment sits one position off relative to every other segment type. field() in messages.js absorbs that rather than making each caller remember it. I did not get this right first time; it showed up as a diff view confidently labelling the wrong MSH field numbers.

The transform stage converts that HL7 into FHIR-style Patient and Observation resources, and back. The round trip is deliberately lossy in exactly eight fields, all routing or bookkeeping metadata: which application and facility sent and received the message (MSH-3..6), the order system's own internal ids (OBR-2/3), and the free-text reference range and abnormal flag on the result (OBX-7/8), which this FHIR subset has no unstructured-text equivalent for. Every clinically meaningful field — identity, name, birth date, sex, the observation code, its value, unit, status and timing — round-trips exactly, and the test proves it by diffing the original against a full HL7 → FHIR → HL7 trip and asserting the diff is precisely those eight fields rather than merely small.

The patient identifier check is deliberately shape-only: ten digits with a calendar-plausible DDMMYY in the first six. Danish CPR numbers historically carried a modulus-11 check digit, but that rule was abolished for numbers issued from 2007 onward, so a modulus check here would reject real people. The page says so next to the editor, not only in the README.

Duplicate detection sits at route, not deliver: each message carries a control id, and a ledger of delivered ids is consulted ahead of the send rather than after it, an Idempotent-Consumer-style check. The test asserts the delivered count directly instead of trusting that the word "duplicate" turned up in a log.

4What was hard

Not the parsing. Pipe-delimited text is simple. The hard part was making each injected fault land on exactly one named stage and no other, which is the only thing that makes the trace view worth looking at. The load-bearing test asserts, for each fault, that every stage before the expected one passed and nothing after the failing stage ran at all. It caught two real bugs before any of this shipped.

Passing it meant deciding which stage owns which check, and there was no single right assignment. The value-range check lives in transform, examining the number just before it becomes a FHIR valueQuantity, rather than in validate beside the identifier check — partly a defensible reading of the boundary between a value that is not a number and one that is not physiologically possible, partly so two faults do not collide on the same box. The source says so in a comment instead of pretending the choice was forced.

5What it is not

  • Not a real integration platform. No broker, no queueing middleware, no persistence beyond an in-memory map, and no authentication, audit logging or consent model — all of which a real clinical integration must have.
  • The HL7 v2 and FHIR support is a small subset. Four segment types and one resource pair. Real interfaces carry dozens of message types; real FHIR servers implement dozens of resources with full terminology binding.
  • All patient data is synthetic. Every name, identifier and result value is invented, and the CPR-shaped identifiers use an obvious placeholder sequence.
  • Nothing real is contacted. The terminology table, the routing table and the "downstream system" are small hand-written objects in pipeline.js.
  • The throughput run is accounting, not a load test. It measures pure JavaScript in one tab with no I/O, and says nothing about what a real engine sustains across real networks.

I have not worked in healthcare integration. This is the machinery as I understand it from the formats and the patterns, built so the parts I claim to understand can be checked.
