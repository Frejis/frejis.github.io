Writeup · A3

A language that works out its own types

7 minute read Hindley-Milner · unification · parsing

Type inference is the part of a compiler that feels like magic until you have implemented it. This one shows its reasoning instead of just its verdict.

Open the demo

1The problem

Anyone who has used OCaml, Haskell, Elm, or the annotation-free corners of TypeScript, Rust and Swift has relied on Hindley-Milner inference. Very few have watched it work. From the outside it is a black box that either stays quiet or produces a message about type variables you never wrote. When it is quiet, it looks like it did nothing. When it complains, it looks arbitrary.

"Understands type systems" on a CV is unfalsifiable. The falsifiable version is a working inference engine that you can feed a broken program and have it point at the right token with a sentence that makes sense.

2What I built

An editor holding a small ML-like language. Nothing in the program says what anything is: no int n, no : string. As you type, the page re-tokenizes, re-parses, re-infers and re-runs the program. It shows the inferred type of the whole expression, underlines anything that cannot work, and prints the result of evaluating it. A panel on the right shows the actual unification steps taken to reach that conclusion, not a summary.

The language has let and let rec, lambdas, if, lists with ::, pairs, string concatenation with ++, the usual arithmetic and comparison operators, and builtins including map, filter, foldl, length, head, tail, fst, snd and show. Broken examples are preloaded so there is something to look at immediately.

3How it works

Three passes, all in DOM-free modules so Node can test them. A hand-written tokenizer attaches a source span to every token. A recursive-descent parser with precedence climbing builds an AST in which every node carries the span of the text it came from. Then Algorithm W: walk the AST bottom-up, invent a fresh type variable wherever the type is not yet known, and emit constraints of the form "these two types must be equal", each labelled with the span it came from and a sentence saying what was being compared.

Solving the constraints is unification. Two type constructors unify when their names and arities match and their arguments unify pointwise; a variable unifies with anything by being substituted, subject to the occurs check. That check is three lines and it is the only thing standing between the engine and an infinite type when someone writes \x -> x x: a would have to equal a -> b, which no finite type satisfies.

The part that makes this Hindley-Milner rather than plain unification is generalization at let. When a let-bound name is inferred, the type variables that are free in its type but not free in the surrounding environment are quantified, producing a type scheme that is instantiated with fresh variables at every use site. That is why let id = \x -> x in (id 1, id true) typechecks, and why the same program with id bound by a lambda must not: a lambda parameter's type is still tied to the enclosing environment, so there is nothing safe to quantify. Both directions are in the test suite, because the wrong version passes the happy path and only fails the counterexample.

4What was hard

Error messages. Textbook unification fails with "cannot unify t3 with t7", which is worthless to a reader. Two things fix that. First, every constraint is created carrying the span and the explanation of why it exists, so a failure can be phrased in the terms on screen: "this list element has type Bool, but the earlier elements have type Int". Second, on a mismatch the reporter names the two whole types the constraint started from rather than the innermost pair that happened to clash — [Int] against [Bool] reads far better than Int against Bool when the reader is looking at two lists. Each broken example has a test asserting both the span and the types named in the message.

The other stubborn one was pixel alignment. The editor is a <textarea> layered over a <pre> that draws the squiggle. Both layers must agree on font, size, line height, padding and wrapping exactly, or the underline drifts a character off the error, which is worse than no underline at all.

5What it is not

  • Not a compiler. No code generation of any kind; the evaluator walks the AST.
  • No modules, records, type classes or user-defined types. One expression per program and a fixed set of builtins.
  • No overloading. + is integers only; == is structural equality. A real language needs type classes or ad-hoc rules here.
  • No mutation, effects or I/O. show returns a string, it does not print.
  • Recursion is stopped, not analysed. A non-terminating program hits a step and depth budget and is reported as a runtime error. There is no totality checking.
  • Type variables are not scoped in error messages the way a mature compiler manages, so a large program's message can name a variable without saying where it came from.
