Hindley-Milner type inference

A small language that works out its own types

Nothing below is annotated with a type, and yet every name has one. Type the program, and the checker figures out what everything must be, complains precisely when it cannot, and then runs it. Edit the code and watch the answers change as you type.

A great deal of software breaks in production for a dull reason: some value was text where the code expected a number, or a list where it expected one item. The mismatch was there the whole time, and nobody noticed until a customer did.

A checker can find those before the program ever runs, and it can do it without anyone writing down what kind of value each name holds — it works that out from how the name is used, and refuses the program if the answers contradict each other. The technical name is type inference. Below, that normally invisible reasoning is shown one step at a time.

    What is actually happening
    
  
    
    
    
      
    Fresh variables
    
      
    When the checker meets \x -> ... it has no idea what
      x is, so it writes down a and carries on.
    
    
    
    
    
      
    Constraints
    
      
    Using x forces the issue. x + 1
      means a ~ Int. Unification solves those equations, or fails with a reason.
    
    
    
    
    
      
    Generalization
    
      
    A let-bound function whose type still has free variables can be
      used at several types at once. That is why id 1 and
      id true both work.
