Integration Trace

A clinical message — the kind a lab result travels in between hospital systems — moving through a seven-stage pipeline: received, parsed, validated, converted between formats, enriched, routed and delivered. Break it a specific way and watch exactly where and why it stops.

Hospital systems send each other messages all day: a lab result, an admission, a prescription. When one of them never arrives, somebody has to work out where along the chain it died and why, and the systems on each end rarely speak the same format. That search is the job this page simulates: seven stages, and the exact one that rejected the message, named.

Every patient name, identifier and value on this page is invented for the demo. The "CPR" numbers are shaped like a real Danish CPR number but use a placeholder sequence no real person carries — see the CPR note below the message editor.

1 · The trace — where a message went, and where it stopped

Green: the stage passed. Red: the stage rejected the message, and this is where it stopped. Grey: the message never reached that stage. Click any box to see exactly what it checked and what it saw.

"It failed somewhere" costs an afternoon of reading logs on both ends. "It failed at validate, on this field, for this reason" costs a minute.

2 · The message editor

Edit the raw message directly, or click a fault button to inject a specific, realistic problem. Each one fails at a different stage — watch the trace above light up somewhere new every time.

Runs automatically as you type, too.

CPR shape check: exactly 10 digits with a calendar-plausible date in the first six. The real modulus-11 check digit was formally abolished for CPR numbers issued from 2007 onward, so this demo only checks shape, not validity — see the README.

Each fault is a real thing that happens in production, and each one stops at a different box — which is what makes the trace above worth trusting rather than decorative.

3 · The same fact, two shapes

The same lab result written twice: on the left the older text format that most Danish hospital integration still runs on, where fields are separated by pipe characters (HL7 v2); on the right the newer structured format many systems are moving towards (FHIR, which is JSON). Translating between them is routine, unglamorous and easy to get subtly wrong, which is why it is shown here rather than asserted in a test.

5 · A throughput run

  

    Push many messages through the pipeline at once with a chosen fault mix,
    and see exactly how many made it and where the rest died. The team this
    demo targets handles roughly 80,000 such messages a day; this in-browser
    run is a toy by comparison — see "what this is not" in the README — but
    the accounting principle is the same one that matters in production: every
    message ends in exactly one terminal state, and the counts must add up.
